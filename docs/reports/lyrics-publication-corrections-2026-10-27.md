# Lyrics publication corrections — 27 October 2026

The publication audit's three findings are corrected in order: scheduled activation, recording identity and atomic album order, then freshness across documents and server-driven changes. A connected track-removal defect was also reproduced and corrected. This release preserves the production base `0f05fa44fc644b86b50ed39bd364da0adaf3d641`, including its newer ownership and playback fixes.

1. **Scheduled activation.** The live activation function failed with PostgreSQL `42702` because its `slug` output parameter conflicted with unqualified `RETURNING slug`. The forward migration qualifies table references, retains the exactly-one-product transaction and idempotency, excludes deleted releases/products, and updates modification timestamps. Cron discovery also excludes deleted releases. Due activation, not-due/repeat no-ops, missing/duplicate/deleted products, archived/deleted releases and service-only execution are covered. Source: [activation migration](../../apps/web/supabase/migrations/20261027021450_repair_scheduled_lyric_publication.sql:7), [cron discovery](../../apps/web/src/app/api/cron/publish-scheduled/route.js:25).

2. **Recording identity and album order.** Reordering uploaded tracks let a position match select another recording before the exact ID match. This caused false audio-change errors for timed lyrics. A single validated ID map now supplies lyric, credit and recording patches; foreign/duplicate/missing targets and overlapping positions fail before storage preparation. The single wizard's null-ID placeholder remains harmless. Separately, row-by-row catalog upserts could not swap unique track numbers. The database now enforces uniqueness through a generated active-number key, defers that constraint during publication, and checks final uniqueness inside the same transaction. Stable slug identity stays immediate. Removed rows retain their IDs, lyrics and history without reserving active order numbers. Source: [shared publication mapping](../../apps/web/src/lib/credits/publication.js:4), [request owner](../../apps/web/src/app/api/admin/releases/[id]/publish/route.js:176), [atomic order migration](../../apps/web/supabase/migrations/20261027021455_atomic_active_catalog_order.sql:7).

   The connected removal function also referenced `tracks.slug`, which does not exist in the live schema (`42703`). It now maps canonical and catalog recordings through `track_id`, locks in the same release → product → canonical tracks → catalog order as publication, and supports requests using either recording ID. Tests cover canonical-ID removal, catalog-ID removal through a product ID, retained history, compaction on republish, and the last-track guard. [Shared removal owner](../../apps/web/supabase/migrations/20261027021455_atomic_active_catalog_order.sql:150).

3. **Catalog and open-modal freshness.** The previous revision store existed only inside one JavaScript document; its deletion poll did not discover ordinary lyric edits or scheduled activation. The shared store now broadcasts invalidations, falls back to storage events, and polls an opaque server version every 30 seconds while visible and online. The version covers source/catalog modification and membership changes plus availability boundaries, so a due release can be discovered without a tab-local admin action. It contains no lyric text, drafts, allocations, credentials or release identities. Unchanged responses do not churn consumers; focus/online recovery, cancellation, timeouts and listener cleanup are covered. Existing catalog and editorial subscribers reload from their authoritative APIs. No player commands or media-engine changes were introduced. [Refresh owner](../../apps/web/src/lib/storefront/catalog-refresh-store.js:9), [server version](../../apps/web/src/lib/media/catalog-refresh-state.js:24), [existing API revision view](../../apps/web/src/app/api/catalog/releases/route.js:24).
