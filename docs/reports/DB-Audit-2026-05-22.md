## Executive summary

The storefront (`artist-platform`) and creator stack (`2MRRW-Control-System`) share one Supabase project in production intent, but maintain **two parallel migration tracks** with overlapping table names and divergent column models. Commerce fulfillment writes **library_items** and **purchases** correctly via service-role webhooks, but **does not persist memberships, collector_ownerships, or vault_entitlements** on payment success despite helper code existing. Subscription checkout creates Stripe subscriptions without any Supabase **memberships** writer or subscription webhook handlers. RLS is generally sound for user-scoped reads; server-only tables rely on service role (correct pattern) with a few tables missing explicit deny policies. Media delivery is **R2-first** in storefront code; Control System still documents Supabase Storage upload paths for ingestion.

## 3. RLS policies & service role usage

### 3.1 Pattern

- **User-facing reads:** `auth.uid() = user_id` (or own profile) on `library_items`, `purchases`, `memberships`, `collector_ownerships`, notifications, vault progress, etc.
- **Writes:** Almost exclusively **`createAdminClient()`** (service role) in API routes and webhooks — bypasses RLS. Correct for entitlements authority.
- **Control System hardening:** `0002_rls_advisor_hardening.sql` adds `using (false)` policies on analytics/server tables.

### 3.2 Gaps

| Table | RLS enabled | Policies | Severity | Notes |
|-------|-------------|----------|----------|-------|
| `processed_stripe_events` | **No** | — | **P1** | Webhook-only writes today; if exposed via anon key + PostgREST, readable/writable |
| `api_rate_limits` | Yes | **None** | P2 | Blocks all non–service-role access (intended server-only) |
| `gift_links`, `gift_link_items` | Yes | No user policies | P2 | Admin routes use service role |
| `notification_events`, `notification_delivery_logs` | Yes | Mostly server-only in CS | P2 | Inbox has user policies |

### 3.3 API routes using service role (sample)

All entitlement-bearing routes use `createAdminClient()` from `@/lib/supabase/admin.js`:

- `/api/account/state` — canonical permission payload
- `/api/webhook` (via `handle-stripe-webhook.js`)
- `/api/library/*`, `/api/vault/*`, `/api/notifications`, `/api/community/*`, admin sync/seed

**Legacy concern (P2):** `save-purchase`, `get-purchases`, `register-user` instantiate `createClient` with **service role key** directly instead of `createAdminClient()` — same privilege, inconsistent pattern.

**No route should use service role on the client/browser** — `admin.js` is server-only; verified not imported in client components in this audit.

## 4. Entitlements flow: webhook → Supabase → `/api/account/state`

### 4.1 Intended architecture (per platform rules)

```
Stripe webhook / confirm
  → fulfill-purchase (purchases + library_items)
  → (should also: memberships, collector_ownerships, vault_entitlements)
  → Supabase tables
  → GET /api/account/state (service role read)
  → AuthContext UI permissions
```

### 4.2 Implemented today

| Step | Status | Detail |
|------|--------|--------|
| Webhook signature + idempotency | **Partial OK** | `processed_stripe_events` dedupe before handler; insert after success. **P1 race** if concurrent duplicate delivery before insert. |
| `payment_intent.succeeded` / `checkout.session.completed` | **OK** | `fulfillPaymentIntent` / `fulfillCheckoutSession` upsert `purchases`, `grantLibraryItems` |
| `charge.refunded` / `payment_intent.canceled` | **Partial** | Revokes `purchases.status`, deletes `library_items` by `purchase_id`. Does **not** revoke `collector_ownerships`, `vault_entitlements`, or `memberships` |
| Subscription lifecycle | **Missing** | No handlers for `customer.subscription.*`, `invoice.paid`, etc. |
| `grantCollectorOwnerships` | **Not wired** | Defined in `collector-ownerships.js`, **never called** from webhook/fulfill |
| `grantVaultPassEntitlement` | **Not wired** | Defined in `vault-entitlements.js`, **never called** from webhook/fulfill |
| `memberships` writes | **Missing** | Only **read** in `account/state`, `entitlements`, `stripe-customers` |
| Membership checkout | **Stripe only** | `/api/memberships/checkout` creates subscription; no Supabase row |
| Client backup fulfill | **OK** | `/api/purchase/confirm` calls `fulfillPaymentIntent` (same library path) |
| Account state | **OK** | Merges library + membership + collector + vault tier + expands digital catalog for subscribers/collectors |

### 4.3 Effective entitlements without DB rows

`account/state` and `entitlements.js` apply **legacy slug heuristics**:

- Collector: slugs `exc-card*`, `exc-bundle*`, `collector-*`, or `collector_ownerships` rows
- Vault pass: slug `vault-pass` / `vault_pass` or `vault_entitlements` row

So collector/vault **may work from library_items slug alone** even when ledger tables are empty — but ledger-backed verification, shipping metadata, and refund revocation are inconsistent.

## 8. Open items & recommendations

### P0 (before production entitlement trust)

1. **Wire fulfillment completely:** After `grantLibraryItems`, call `grantCollectorOwnerships` and `grantVaultPassEntitlement` from `fulfill-purchase.js` (or webhook handler) with payment/session object.
2. **Subscription → Supabase:** Handle `customer.subscription.created|updated|deleted` (and/or `invoice.paid`) to upsert `memberships` (`status`, `stripe_subscription_id`, `current_period_end`).
3. **Retire or fix `register-user`:** Point to guest auth flow / `profiles`; remove `users` table reference.
4. **Migration reconciliation:** Document and run one authoritative ordering for shared DB; resolve `media_playback_progress` column model vs live DB.

### P1 (launch hardening)

5. **Refund parity:** On refund/cancel, revoke matching `collector_ownerships`, `vault_entitlements`, and membership status.
6. **Slug governance:** Enforce slug existence at checkout creation (fail fast) or auto-upsert from cart catalog snapshot.
7. **Apply Control 0020+** on production if storefront reads `gifting_enabled`, `content_type`.
8. **Transactional idempotency:** Insert `processed_stripe_events` in same logical unit as fulfill, or use Stripe id as idempotency key on upserts only with advisory lock.
9. **RLS on `processed_stripe_events`:** `ENABLE ROW LEVEL SECURITY` + deny-all policy for `authenticated`/`anon`.

### P2 (quality / ops)

10. Remove or populate empty `20260516222800_community_circle_system.sql`.
11. Consolidate migration manifest across repos in `docs/reports/` or Supabase linked folder.
12. Standardize on `createAdminClient()` in legacy purchase routes.
13. Live Supabase advisor pass (`get_advisors` security) when MCP/CLI available — complements this static audit.
